# PRODUCT VISION

We are developing a **white-label desktop retail management system for shoe retailers**.

The same software skeleton/core product will be developed once and then installed independently for different shoe retailers.

This is NOT currently designed as a traditional multi-tenant SaaS platform.

The core commercial principle is:

> **One Codebase → Many Independent Installations**

Each retailer receives its own deployment and its own database.

Example:

                    SHOE RETAIL CORE
                          │
            ┌─────────────┼─────────────┐
            │             │             │
            ▼             ▼             ▼
         STORE A        STORE B       STORE C
            │             │             │
         WPF A          WPF B         WPF C
            │             │             │
         API A          API B         API C
            │             │             │
     PostgreSQL A   PostgreSQL B  PostgreSQL C

There is **one main source-code repository**.

We must NOT create long-lived customer-specific forks such as:

StoreAProject
StoreBProject
StoreCProject

because they would diverge over time.

Instead:

                   ShoeRetail Core
                         │
               Configuration/Branding
               ┌─────────┼─────────┐
               ▼         ▼         ▼
            Store A   Store B   Store C

Customer-specific differences should preferably be configuration, branding, feature flags, or extension points.

Avoid code such as:

if (customerName == "ABC")
{
    // custom hack
}

unless absolutely unavoidable.

# ORDER REQUEST + SELLER APPROVAL — CRITICAL BUSINESS RULE

Customer orders must NOT instantly become finalized sales.

The user proposed and we accepted this workflow:

CUSTOMER

Select Products
      ↓
Send Order Request
      ↓
PENDING APPROVAL
      ↓
Request appears in Seller system
      ↓
Seller reviews request
     ┌──────────────┐
     │              │
  APPROVE         REJECT
     │              │
     ▼              ▼
 Confirmed        Rejected
     │
     ▼
Physical stock committed
     │
     ▼
Preparing
     ↓
Ready
     ↓
Delivered

However, there is a concurrency problem if stock is not protected while waiting for seller approval.

Therefore the agreed approach is:

> **Pending order requests reserve stock but do not immediately reduce physical stock.**

Example:

Before request:

QuantityOnHand = 10
Reserved        = 0
Available       = 10

Customer requests 2:

QuantityOnHand = 10
Reserved        = 2
Available       = 8

Seller rejects:

QuantityOnHand = 10
Reserved        = 0
Available       = 10

Seller approves:

QuantityOnHand = 8
Reserved        = 0
Available       = 8

Thus:

> Seller approval causes the physical stock reduction.

The initial customer request causes only reservation.

These operations must be transaction-safe to prevent two customers from buying/reserving the same final unit incorrectly.

# ORDER APPROVAL TRANSACTION

When Seller approves a Pending order, conceptually the backend should perform atomically:

1. Verify Order is Pending.
2. Verify reservation is still valid.
3. Verify quantities.
4. Set ApprovalStatus = Approved.
5. QuantityOnHand -= quantity.
6. ReservedQuantity -= quantity.
7. Create InventoryMovement.
8. Create PaymentPlan.
9. Create Installments.
10. Create AccountTransaction: +OrderTotal.
11. Create OrderHistory.
12. Create AuditLog.
13. COMMIT.

If any part fails:

ROLLBACK

We must NEVER end in a state such as:

Order = Approved
but
Current Account debt not created

or:

Stock decreased
but
Order approval failed.

---

# ORDER REJECTION TRANSACTION

Conceptual flow:

1. Order Pending → Rejected.
2. ReservedQuantity -= reserved quantity.
3. Create ReservationReleased InventoryMovement.
4. OrderHistory.
5. AuditLog.
6. COMMIT.

Physical QuantityOnHand does not decrease.

PaymentPlan does not become active / is not created as final debt.

Current-account debt is not created.

---

# CUSTOMER ORDER REQUEST TRANSACTION

When Customer sends an order request:

1. Authenticate user.
2. Verify Customer role.
3. Validate Product.
4. Validate Variant.
5. Check IsActive.
6. Check available stock.
7. Read CURRENT SalePrice from database.
8. Read purchase-price snapshot internally.
9. Create Order with Pending approval.
10. Create OrderItems with snapshots.
11. ReservedQuantity += requested quantity.
12. Create InventoryMovement: reservation.
13. Create OrderHistory.
14. Create AuditLog if desired.
15. COMMIT.

All must be transaction-safe.

---

# PAYMENT TRANSACTION

Conceptual backend operation:

1. Create Payment.
2. Find oldest overdue/open Installments.
3. Automatically allocate 25,000.
4. Create PaymentAllocations.
5. Create AccountTransaction = -25,000.
6. Create AuditLog.

# PAYMENT REVERSAL TRANSACTION

1. Validate active Payment.

# IMPORTANT INVARIANTS

13. Pending order reserves stock.
14. Physical stock is decreased upon Seller approval.
15. Financial correction uses reversal/correction rather than silent deletion.
