# STEP 2.2 — Final Database Blueprint

Bu belge, `docs/00-handoff/` içindeki mantıksal tasarımın (16 tablo) fiziksel
PostgreSQL şemasına dönüştürülmesi sürecini kaydeder. Her oturumda buraya
eklenerek büyütülecektir.

Durum: **Devam ediyor.** Tamamlanan: ortak kararlar + `users`, `customers`, `products`, `product_variants` tabloları.

> **Uygulama sırası notu:** `users.customer_id`, `customers(id)`'e FK veriyor. Bu yüzden
> nihai `schema.sql`'de fiziksel oluşturma sırası `customers` → `users` olacak
> (bu dokümanda tartışma sırası farklı olsa da). 16 tablo bitince tüm bağımlılık
> sırasını tek seferde gözden geçireceğiz.

## Ortak Kararlar (tüm tablolara uygulanır)

| Konu | Karar | Gerekçe (özet) |
|---|---|---|
| Primary Key | `bigint GENERATED BY DEFAULT AS IDENTITY` | Tek DB / tek mağaza modeli, dağıtık senkronizasyon yok → UUID'e gerek yok. Daha küçük, daha hızlı index. |
| Zaman damgası | `timestamptz`, UTC olarak | Saat dilimi belirsizliğini önler. `Installment.DueDate` istisna: `date` tipinde (saat anlamsız). |
| Enum saklama | `varchar` + `CHECK` constraint | Okunabilirlik önceliklendirildi (küçük ölçek, kaynak kodu devri senaryosu). `smallint`'e göre performans farkı önemsiz. |
| Para alanları | `numeric(18,2)` | `float`/`double` asla kullanılmaz (ikili kayan nokta hataları). 18 basamak fazlasıyla yeterli. |
| FK silme davranışı | Varsayılan `ON DELETE RESTRICT` | Hard-delete politikası zaten yasak; RESTRICT ek güvenlik ağı. `CASCADE` istisnai durumlar dışında kullanılmaz. |
| İsimlendirme | Fiziksel şemada `snake_case`, C# tarafında `PascalCase` | PostgreSQL ekosistemiyle (psql, pgAdmin, raporlama) uyum. EF Core naming convention ile eşlenecek. |

## Tablo 1/16 — `users`

```sql
CREATE TABLE users (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username              varchar(100)  NOT NULL,
    normalized_username   varchar(100)  NOT NULL,
    password_hash         text          NOT NULL,
    role                  varchar(20)   NOT NULL,
    customer_id           bigint        NULL,
    is_active             boolean       NOT NULL DEFAULT true,
    created_at            timestamptz   NOT NULL DEFAULT now(),
    updated_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_users_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,

    CONSTRAINT chk_users_role
        CHECK (role IN ('Seller', 'Customer')),

    CONSTRAINT chk_users_role_customer_consistency
        CHECK (
            (role = 'Seller'  AND customer_id IS NULL) OR
            (role = 'Customer' AND customer_id IS NOT NULL)
        )
);

CREATE UNIQUE INDEX ux_users_normalized_username ON users (normalized_username);
CREATE INDEX ix_users_customer_id ON users (customer_id);
```

**Notlar:**
- `password_hash` → `text` (varchar(n) ile performans farkı yok; hash uzunluğu algoritmaya göre değişebilir).
- `normalized_username` → case-insensitive login için ayrı kolon + unique index.
- `chk_users_role_customer_consistency` → iş kuralını DB seviyesinde de zorlar (defense in depth).
- `ix_users_customer_id` → PostgreSQL FK kolonlarına otomatik index eklemez, elle eklenmesi gerekir.
- `updated_at` otomatik güncellenmiyor henüz — Faz 4'te (Backend Foundation) trigger veya EF Core `SaveChanges` override ile ele alınacak.

## Tablo 2/16 — `customers`

```sql
CREATE TABLE customers (
    id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    customer_type     varchar(20)   NOT NULL,

    full_name         varchar(200)  NULL,
    company_name      varchar(200)  NULL,
    contact_person    varchar(200)  NULL,

    phone             varchar(30)   NOT NULL,
    email             varchar(255)  NULL,

    tax_number        varchar(50)   NULL,
    tax_office        varchar(100)  NULL,

    billing_address   text          NULL,
    delivery_address  text          NULL,
    notes             text          NULL,

    is_active         boolean       NOT NULL DEFAULT true,
    created_at        timestamptz   NOT NULL DEFAULT now(),
    updated_at        timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT chk_customers_type
        CHECK (customer_type IN ('Individual', 'Corporate')),

    CONSTRAINT chk_customers_type_name_consistency
        CHECK (
            (customer_type = 'Individual' AND full_name    IS NOT NULL) OR
            (customer_type = 'Corporate'  AND company_name IS NOT NULL)
        ),

    CONSTRAINT chk_customers_phone_not_blank
        CHECK (btrim(phone) <> '')
);

CREATE INDEX ix_customers_phone         ON customers (phone);
CREATE INDEX ix_customers_full_name     ON customers (full_name);
CREATE INDEX ix_customers_company_name  ON customers (company_name);
```

**Notlar:**
- `chk_customers_type_name_consistency` → `users` tablosundaki "role'e göre zorunlu alan" deseninin tekrarı. Tekrar eden iş kuralı desenleri projede tutarlı şekilde uygulanacak.
- `chk_customers_phone_not_blank` → `NOT NULL`, boş string'i (`''`) engellemez, sadece `NULL`'ı engeller. `btrim(phone) <> ''` gerçek bir değer girildiğini garanti eder.
- `phone` bilinçli olarak `UNIQUE` değil — farklı müşteriler meşru şekilde aynı numarayı paylaşabilir (handoff kararı).
- `tax_number` şimdilik `UNIQUE` değil (iş gereksinimi net değil). İleride gerekirse partial unique index ile eklenebilir:
  `CREATE UNIQUE INDEX ux_customers_tax_number ON customers (tax_number) WHERE tax_number IS NOT NULL;`
- Arama index'leri şimdilik standart `btree`. Kısmi/bulanık arama (`ILIKE '%ahmet%'`) gerekirse ileride `pg_trgm` eklentisiyle güçlendirilecek (Faz 10'da ele alınacak, V1 kapsamını şişirmemek için şimdi eklenmiyor).
- `billing_address`, `delivery_address`, `notes` → `text` (uzunluk sınırına gerek yok, `varchar(n)` ile performans farkı yok).
- `customers` tablosunun hiçbir FK'si yok (temel/kök varlık) — bu yüzden burada delete-behavior kararı gerekmiyor.

## Tablo 3/16 — `products`

```sql
CREATE TABLE products (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    name          varchar(200)  NOT NULL,
    brand         varchar(100)  NULL,
    model         varchar(100)  NULL,
    category      varchar(100)  NULL,
    material      varchar(100)  NULL,
    description   text          NULL,

    is_active     boolean       NOT NULL DEFAULT true,
    created_at    timestamptz   NOT NULL DEFAULT now(),
    updated_at    timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT chk_products_name_not_blank
        CHECK (btrim(name) <> '')
);

CREATE INDEX ix_products_name   ON products (name);
CREATE INDEX ix_products_brand  ON products (brand);
```

**Notlar:**
- `category` ve `brand` bilinçli olarak düz metin, ayrı lookup tablo (`Categories`/`Brands`) + FK değil. Handoff'taki 16 tablo listesinde bu tablolar yok; `Material` gibi V1'de basit tutuluyor. İleride marka/kategori sayısı artıp tutarsızlık sorunu çıkarsa (`"Nike"` vs `"nike"` gibi), lookup tabloya normalize edilebilir — bilinçli bir "basit tut" kararı, hata değil.
- `chk_products_name_not_blank` → `customers.phone` ile aynı desen (NOT NULL boş string'i durdurmaz).
- Arama index'leri sadece `name` ve `brand` — `SKU`/`Barcode` araması `product_variants` seviyesinde olacak. `category` için şimdilik index yok (handoff'taki arama listesinde yer almıyor); ihtiyaç çıkarsa eklenecek.
- FK yok — kök varlık, `product_variants`'ın parent'ı.

## Tablo 4/16 — `product_variants`

```sql
CREATE TABLE product_variants (
    id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id       bigint        NOT NULL,

    size             varchar(20)   NOT NULL,
    color            varchar(50)   NOT NULL,

    sku              varchar(50)   NOT NULL,
    barcode          varchar(50)   NULL,

    purchase_price   numeric(18,2) NOT NULL,
    sale_price       numeric(18,2) NOT NULL,

    is_active        boolean       NOT NULL DEFAULT true,
    created_at       timestamptz   NOT NULL DEFAULT now(),
    updated_at       timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_product_variants_product
        FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT,

    CONSTRAINT chk_product_variants_size_not_blank
        CHECK (btrim(size) <> ''),

    CONSTRAINT chk_product_variants_color_not_blank
        CHECK (btrim(color) <> ''),

    CONSTRAINT chk_product_variants_sku_not_blank
        CHECK (btrim(sku) <> ''),

    CONSTRAINT chk_product_variants_purchase_price_nonneg
        CHECK (purchase_price >= 0),

    CONSTRAINT chk_product_variants_sale_price_nonneg
        CHECK (sale_price >= 0)
);

CREATE UNIQUE INDEX ux_product_variants_sku
    ON product_variants (sku);

CREATE UNIQUE INDEX ux_product_variants_barcode
    ON product_variants (barcode) WHERE barcode IS NOT NULL;

CREATE UNIQUE INDEX ux_product_variants_product_size_color
    ON product_variants (product_id, size, color);

CREATE INDEX ix_product_variants_product_id
    ON product_variants (product_id);
```

**Notlar:**
- `size` → `varchar(20)`, sayısal değil. Ayakkabı bedenleri `42`, `42.5`, `42 2/3` gibi kesirli/özel notasyonlar alabiliyor.
- `ux_product_variants_barcode` → partial unique index. Barkod opsiyonel ama girildiğinde benzersiz olmalı; `WHERE barcode IS NOT NULL` sadece dolu satırlarda benzersizliği zorluyor.
- `ux_product_variants_product_size_color` → composite unique index, aynı üründe aynı beden+renk kombinasyonunun tekrarını engeller.
- `sale_price >= purchase_price` gibi bir kısıt BİLİNÇLİ OLARAK eklenmedi — bu bir veri bütünlüğü kuralı değil, iş kararı (zararına satış meşru bir senaryo olabilir). Böyle "yumuşak" kurallar Application katmanında ele alınacak.
- `ON DELETE RESTRICT` → global politika: `products` zaten hard-delete edilmiyor, bu ek bir güvenlik ağı.
