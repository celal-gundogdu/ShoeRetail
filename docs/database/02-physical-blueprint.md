## Ortak Kararlar (tüm tablolara uygulanır)

| Konu | Karar | Gerekçe (özet) |
|---|---|---|
| Birincil anahtar | `bigint GENERATED BY DEFAULT AS IDENTITY` | Her kurulum kendi veritabanına sahip, dağıtık senkronizasyon yok → UUID gereksiz. Daha küçük, daha hızlı index. |
| Zaman damgası | `timestamptz`, UTC | Saat dilimi belirsizliğini önler. Saat anlamı olmayan iş tarihleri (`due_date` gibi) `date` tipinde. |
| Enum saklama | `varchar` + `CHECK` | Okunabilirlik önceliklendirildi (küçük ölçek, kaynak kodu devri senaryosu). `smallint`'e göre performans farkı önemsiz; `SELECT` çıktısı doğrudan okunabilir olur. |
| Para | `numeric(18,2)` | `float`/`double` **asla** — ikili kayan nokta hataları parayı bozar. |
| Miktar | `integer` | Adet sayıları için fazlasıyla yeterli. |
| FK silme davranışı | Varsayılan `ON DELETE RESTRICT` | Hard-delete zaten yasak; RESTRICT ek güvenlik ağı. `CASCADE` gerekçesiz kullanılmaz. |
| İsimlendirme | Fiziksel `snake_case`, C# `PascalCase` | PostgreSQL ekosistemiyle (psql, pgAdmin, raporlama) uyum. EF Core naming convention köprüler. |

### Tekrar Eden Desenler

Bunlar tüm tablolarda tutarlı şekilde uygulanır:

**1. Tipe bağlı zorunlu alan**
Bir alanın zorunluluğu başka bir alanın değerine bağlıysa, `CHECK` ile zorlanır:
```sql
CHECK (
    (role = 'Owner'        AND supplier_id IS NULL) OR
    (role = 'Manufacturer' AND supplier_id IS NOT NULL)
)
```

**2. Boş string koruması**
`NOT NULL` yalnızca `NULL`'ı engeller, `''` (boş string) geçer. Gerçekten dolu olması
gereken metin alanlarına ek kısıt:
```sql
CHECK (btrim(phone) <> '')
```

**3. Opsiyonel ama girildiğinde benzersiz**
Kısmi (partial) unique index:
```sql
CREATE UNIQUE INDEX ux_product_variants_barcode
    ON product_variants (barcode) WHERE barcode IS NOT NULL;
```

**4. FK kolonlarına elle index**
PostgreSQL, foreign key kolonlarına **otomatik index eklemez**. Her FK için index elle
yazılır (JOIN performansı ve parent silme/kilit davranışı için).

**5. `updated_at` henüz otomatik değil**
`DEFAULT now()` yalnızca INSERT anında çalışır. UPDATE'te tazelenmesi için
Faz 4'te karar verilecek: PostgreSQL `BEFORE UPDATE` trigger'ı (DB seviyesinde garanti)
veya EF Core `SaveChanges` override (uygulama seviyesinde). Şimdilik açık bırakıldı.

### DB Kısıtı mı, Uygulama Kuralı mı?

| Veritabanında | Uygulama katmanında |
|---|---|
| Tek satırla doğrulanabilen kurallar | Çok satırlı / çok tablolu kurallar |
| `quantity_on_hand >= 0` | `SUM(installments.amount) = order.total_amount` |
| `amount > 0` | "Müsait stoktan fazla sipariş verilemez" |
| `quantity_reserved <= quantity_on_hand` | Yetkilendirme, iş akışı geçişleri |

Sebep: DB kısıtları hangi kod yazarsa yazsın devreye girer — son savunma hattıdır.
Ama çok satırlı kuralları DB'de zorlamak (trigger, exclusion constraint) bu ölçekte
gereksiz karmaşıklık yaratır.

## Tablolar

### Tablo 1/22 — `store_profile`

Tek satırlık işletme yapılandırması. Bağımsız (FK yok), bu yüzden ilk sırada.
Stok kodu üretim kuralı burada yaşadığı için `products` tablosundan **önce** gelmesi
kavramsal olarak da doğru.

```sql
CREATE TABLE store_profile (
    id                    smallint      PRIMARY KEY DEFAULT 1,

    store_name            varchar(200)  NOT NULL,
    phone                 varchar(30)   NULL,
    email                 varchar(255)  NULL,
    address               text          NULL,
    tax_number            varchar(50)   NULL,
    tax_office            varchar(100)  NULL,

    currency_code         char(3)       NOT NULL DEFAULT 'TRY',

    stock_code_prefix     varchar(5)    NOT NULL DEFAULT 'GND',
    stock_code_digits     smallint      NOT NULL DEFAULT 6,

    default_low_stock_threshold  integer NOT NULL DEFAULT 5,

    updated_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT chk_store_profile_singleton
        CHECK (id = 1),
    CONSTRAINT chk_store_profile_name_not_blank
        CHECK (btrim(store_name) <> ''),
    CONSTRAINT chk_store_profile_currency_format
        CHECK (currency_code ~ '^[A-Z]{3}$'),
    CONSTRAINT chk_store_profile_stock_prefix_format
        CHECK (stock_code_prefix ~ '^[A-Z]{2,5}$'),
    CONSTRAINT chk_store_profile_stock_digits_range
        CHECK (stock_code_digits BETWEEN 4 AND 8),
    CONSTRAINT chk_store_profile_low_stock_nonneg
        CHECK (default_low_stock_threshold >= 0)
);

INSERT INTO store_profile (store_name) VALUES ('Mağaza Adı');
```

#### "Singleton" (tek satırlık) tablo problemi

Bu tablo bir *koleksiyon* değil — sistemde **tam olarak bir tane** mağaza profili
olmalıdır. Ama normal bir tablo istediği kadar satır kabul eder; ikinci bir satır
girilirse uygulama "hangisi doğru?" diye şaşırır.

| Yöntem | Değerlendirme |
|---|---|
| Uygulama koduyla kontrol | ❌ Zayıf — pgAdmin'den elle satır eklenirse çöker |
| Sabit ifade üzerine unique index | ⚠️ Çalışır ama okunması zor, egzotik |
| **`id` kolonunu 1'e sabitlemek** | ✅ Basit, okunur, DB seviyesinde garanti |

Seçilen: `id smallint PRIMARY KEY DEFAULT 1` + `CHECK (id = 1)`.
İkinci satır `id=1` ile eklenirse PK çakışması, `id=2` ile eklenirse CHECK ihlali alır.
Yapısal olarak imkânsız hale gelir.

> ⚠️ **Bilinçli konvansiyon istisnası:** Ortak karar "her PK `bigint identity`" idi.
> Burada `smallint` + sabit değer kullanıldı; `identity` (otomatik artan) mantığı tekil
> yapılandırma kaydında zararlı olurdu. **22 tablodaki tek istisna budur.**

#### Kolon gerekçeleri

- **`store_name`** — Zorunlu. `btrim` kontrolü var çünkü `NOT NULL` boş string'i (`''`)
  engellemez, sadece `NULL`'ı engeller. (Tekrar eden desen #2.)
- **`tax_number` / `tax_office`** — Yazdırılan belgeler için (sipariş fişi, sevk
  listesi). Bir toptancının çıkardığı belgede kendi vergi bilgisi bulunur.
- **`currency_code`** — `char(3)`, ISO 4217 (`TRY`, `USD`, `EUR`). `varchar` değil
  `char`: uzunluk her zaman tam 3, değişken değil — tip kuralı kendisi anlatıyor.
  `CHECK` ile büyük harf zorlanıyor, `try`/`TRY` karışıklığı olmasın diye.
- **`stock_code_prefix` + `stock_code_digits`** — 🔑 Bu tablonun asıl varlık sebebi.
  Neden config dosyasında değil de veritabanında: ilkemiz *"veritabanı → iş bilgisi,
  config dosyası → marka/dağıtım bilgisi"*. Stok kodu öneki ilk bakışta marka gibi
  görünür ama **veri bütünlüğünü etkiler** — biri config dosyasında `GND`'yi `ABC`
  yaparsa mevcut tüm `GND...` kodları aniden "geçersiz format" olur. Bu bilgi,
  koruduğu veriyle aynı yerde yaşamalıdır. Logo ve renkler config dosyasında kalır;
  onlar gerçekten sadece görseldir.
- **`default_low_stock_threshold`** — Yeni oluşturulan varyantlara uygulanacak
  başlangıç eşiği. Asıl eşik varyant başına `inventory` tablosunda duracak, ama
  ~4800 varyanta elle eşik girmek imkânsız olduğu için fabrika ayarı görevi görür.
  Kullanıcı isterse tek tek ince ayar yapar. ("Az tık" ilkesinin somut karşılığı.)
- **`updated_at` var, `created_at` yok** — Kurulumda otomatik oluşan tekil bir kayıt
  için "ne zaman oluştu" bilgisinin iş değeri yok; "ne zaman değiştirildi" var.
- **FK yok** — Kök tablo, kimseye referans vermiyor; silme davranışı kararı gerekmiyor.

#### Doğrulama testleri

```sql
-- 1) Tek satır oluştu mu?
SELECT * FROM store_profile;
-- Beklenen: id=1, currency_code='TRY', stock_code_prefix='GND', stock_code_digits=6

-- 2) İkinci satır eklenemez
INSERT INTO store_profile (id, store_name) VALUES (2, 'Sahte');
-- Beklenen HATA: chk_store_profile_singleton

-- 3) Geçersiz önek reddedilir
UPDATE store_profile SET stock_code_prefix = 'gnd';
-- Beklenen HATA: chk_store_profile_stock_prefix_format

-- 4) Boş isim reddedilir
UPDATE store_profile SET store_name = '   ';
-- Beklenen HATA: chk_store_profile_name_not_blank

-- 5) Geçerli güncelleme çalışır
UPDATE store_profile
SET store_name = 'Gündoğdu Ayakkabı', phone = '0212 555 00 00', updated_at = now();
-- Beklenen: UPDATE 1
```

### Tablo 2/22 — `customers`

Perakendeci müşteriler. **Sisteme giriş yapmazlar** — sadece veri kaydıdır.

#### Pivot etkisi

| | Pivot öncesi | Şimdi |
|---|---|---|
| Kim | Perakendeci mağaza | Perakendeci mağaza (aynı) |
| Sisteme girer mi | ✅ Kendi hesabıyla | ❌ Hayır |
| `users` ile bağ | `users.customer_id` FK vardı | **Bağ koptu** |

Tablonun yapısı büyük ölçüde korundu; etrafındaki ilişki gitti. Karşılığı `users`
tablosunda görülecek.

#### Toptancı işine özgü eklemeler (pivot sonrası)

- **`city` / `district`** — Adres serbest `text` olduğu için içinde şehir aranamıyordu.
  Ayrı kolonlar: bölge filtresi, sevkiyat gruplaması, bölgesel satış raporu.
- **`default_payment_term_days`** — Müşteriyle anlaşılan vade (ör. 60 gün). Sipariş
  sevk edilirken ödeme planındaki vade tarihi bundan **otomatik** hesaplanır; kullanıcı
  elle tarih girmez, sadece onaylar.
- **`credit_limit`** — Müşteri borç tavanı. **Limit aşımı DB'de engellenmez** —
  Application katmanı uyarır, kullanıcı onaylarsa işlem devam eder. Gerekçe: bu bir
  veri bütünlüğü kuralı değil iş kararıdır; gerçek hayatta "bu müşteriyi tanıyorum,
  bu seferlik geçsin" durumu sık olur ve yazılım patronu kilitlememelidir.

```sql
CREATE TABLE customers (
    id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    customer_type     varchar(20)   NOT NULL,

    full_name         varchar(200)  NULL,   -- Individual için zorunlu
    company_name      varchar(200)  NULL,   -- Corporate için zorunlu
    contact_person    varchar(200)  NULL,

    phone             varchar(30)   NOT NULL,
    email             varchar(255)  NULL,

    tax_number        varchar(50)   NULL,
    tax_office        varchar(100)  NULL,

    city              varchar(100)  NULL,
    district          varchar(100)  NULL,
    billing_address   text          NULL,
    delivery_address  text          NULL,

    default_payment_term_days  smallint       NULL,
    credit_limit               numeric(18,2)  NULL,

    notes             text          NULL,

    is_active         boolean       NOT NULL DEFAULT true,
    created_at        timestamptz   NOT NULL DEFAULT now(),
    updated_at        timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT chk_customers_type
        CHECK (customer_type IN ('Individual', 'Corporate')),
    CONSTRAINT chk_customers_type_name_consistency
        CHECK (
            (customer_type = 'Individual' AND full_name    IS NOT NULL) OR
            (customer_type = 'Corporate'  AND company_name IS NOT NULL)
        ),
    CONSTRAINT chk_customers_phone_not_blank
        CHECK (btrim(phone) <> ''),
    CONSTRAINT chk_customers_payment_term_nonneg
        CHECK (default_payment_term_days IS NULL OR default_payment_term_days >= 0),
    CONSTRAINT chk_customers_credit_limit_nonneg
        CHECK (credit_limit IS NULL OR credit_limit >= 0)
);

CREATE INDEX ix_customers_phone         ON customers (phone);
CREATE INDEX ix_customers_full_name     ON customers (full_name);
CREATE INDEX ix_customers_company_name  ON customers (company_name);
CREATE INDEX ix_customers_city          ON customers (city);
```

#### Gerekçeler

- **`customer_type` hâlâ gerekli** — Müşterilerimiz mağaza ama hepsi şirket değil;
  esnaf/şahıs işletmesi de var. Kurumsalda ünvan+vergi bilgisi, şahısta ad-soyad
  anlamlıdır. İkisi de zorunlu yapılamayacağı için **tipe bağlı zorunluluk deseni**
  (Tekrar Eden Desen #1) uygulanır.
- **`phone` zorunlu ama `UNIQUE` değil** — Bilinçli. İki farklı mağaza meşru şekilde
  aynı numarayı paylaşabilir (aynı patronun iki dükkânı, ortak muhasebeci numarası).
  Benzersizlik zorlanırsa gerçek veri reddedilir.
- **`NULL` kabul eden alanlarda `CHECK` yazımı** — `CHECK (credit_limit IS NULL OR
  credit_limit >= 0)`. PostgreSQL'de `NULL >= 0` sonucu `TRUE` değil `NULL`'dır ve
  `CHECK` kısıtı `NULL` sonucu geçerli sayar; bu örnekte şans eseri doğru çalışırdı,
  ama niyeti açıkça yazmak ileride yanlış anlaşılmayı önler.
- **`smallint` (`default_payment_term_days`)** — −32.768…+32.767. 90 günlük vade bile
  fazlayken 32 bin gün (89 yıl) kâfi. Küçük tip = küçük index.
- **`tax_number` hâlâ `UNIQUE` değil** — Risk biliniyor: aynı müşteri iki kez
  girilirse ("ABC Ayakkabı" / "ABC AYAKKABI LTD") cari hesap ikiye bölünür. Ama
  benzersizlik meşru durumları da engeller (aynı vergi numaralı iki şube). Çözüm
  DB'de değil UI'da: yeni kayıtta *"Benzer bir kayıt var: … — bu mu?"* uyarısı
  (Faz 9).
- **Arama index'leri standart `btree`** — `LIKE 'ahmet%'` (baştan eşleşme) hızlanır,
  `ILIKE '%ahmet%'` (ortadan arama) hızlanmaz. Gerçek kullanımda ortadan arama
  istenirse `pg_trgm` + GIN index eklenecek. Veri yokken ölçmeden optimize etmek
  erken olur.
- **FK yok** — kök tablo.

#### Doğrulama testleri


### Tablo 3/22 — `suppliers` 🆕

Üreticiler. Pivot'un getirdiği en önemli yapısal ekleme — üretici artık sadece "mal
aldığımız yer" değil, **sisteme giriş yapan kullanıcı**.

#### Bilinçli asimetri: neden `customers` ile aynı yapıda değil

| | `customers` | `suppliers` |
|---|---|---|
| Tip ayrımı | `Individual` / `Corporate` | ❌ Yok |
| Kimlik alanı | `full_name` **veya** `company_name` | Sadece `company_name` |
| Sisteme girer mi | ❌ Hayır | ✅ Evet |
| Risk limiti | ✅ Var | ❌ Yok |

- **Tip ayrımı yok:** Ayakkabı üreticisi her zaman firmadır (imalathane/fabrika).
  Şahıs olarak toptan ayakkabı üreten bir taraf pratikte yoktur. Müşteri tarafında
  esnaf/şahıs işletmesi gerçek bir senaryoydu, burada değil. Sonuç: `company_name
  NOT NULL`, tipe bağlı `CHECK` karmaşasına gerek yok.
  **Gereksiz simetri kurmak da bir over-engineering biçimidir.**
- **Risk limiti yok:** `credit_limit`, *bizim* müşteriye açtığımız kredinin tavanıydı.
  Üretici tarafında tavanı onlar koyar, biz değil — bizde modellenmesi anlamsız.

```sql
CREATE TABLE suppliers (
    id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    company_name      varchar(200)  NOT NULL,
    contact_person    varchar(200)  NULL,

    phone             varchar(30)   NOT NULL,
    email             varchar(255)  NULL,

    tax_number        varchar(50)   NULL,
    tax_office        varchar(100)  NULL,

    city              varchar(100)  NULL,
    district          varchar(100)  NULL,
    address           text          NULL,

    default_payment_term_days  smallint  NULL,   -- borcumuzun vadesi (gün)
    default_lead_time_days     smallint  NULL,   -- ortalama termin süresi (gün)

    notes             text          NULL,

    is_active         boolean       NOT NULL DEFAULT true,
    created_at        timestamptz   NOT NULL DEFAULT now(),
    updated_at        timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT chk_suppliers_company_name_not_blank
        CHECK (btrim(company_name) <> ''),
    CONSTRAINT chk_suppliers_phone_not_blank
        CHECK (btrim(phone) <> ''),
    CONSTRAINT chk_suppliers_payment_term_nonneg
        CHECK (default_payment_term_days IS NULL OR default_payment_term_days >= 0),
    CONSTRAINT chk_suppliers_lead_time_nonneg
        CHECK (default_lead_time_days IS NULL OR default_lead_time_days >= 0)
);

CREATE INDEX ix_suppliers_company_name ON suppliers (company_name);
CREATE INDEX ix_suppliers_phone        ON suppliers (phone);
```

#### İki ticari koşul alanı

- **`default_payment_term_days`** — "Bu üreticiyle 90 gün vade çalışıyoruz."
  Mal kabul yapılınca borcun vadesi otomatik hesaplanır.
- **`default_lead_time_days`** — "Bu üreticiye sipariş verince ortalama 30 günde
  gelir." Satın alma siparişinde tahmini teslim tarihini otomatik doldurur ve
  dashboard'daki *"bu sipariş gecikti"* uyarısını mümkün kılar.

Her ikisi de "kullanıcı yazmasın, sistem doldursun" ilkesinin uygulaması.

#### Gerekçeler

- **`company_name` `UNIQUE` değil** — Üretici sayısı az (birkaç firma), mükerrer kayıt
  riski insan gözüyle fark edilir. Benzersizlik zorlamak aynı grubun iki ayrı
  imalathanesi gibi meşru durumları engelleyebilir.
- **`email` `NULL` kabul ediyor** — Giriş `username` ile yapılacak, e-posta ile değil.
  E-posta burada sadece iletişim bilgisidir. "Şifremi unuttum" akışı gelirse o zaman
  zorunlu hale getirilir; henüz kullanılmayan bir alanı doldurmaya mecbur bırakmak
  gereksizdir.
- **🔴 Gizlilik notu** — Bu tablo, üretici kullanıcısının kendi kaydını görebileceği
  tek yerdir. `suppliers` tablosunun tamamını **asla** göremez; başka üreticilerin

### Tablo 4/22 — `users`

Giriş yapan kimlikler. Pivot'tan en çok etkilenen tablo.

#### Pivot etkisi

```
ÖNCE                                    ŞİMDİ
─────                                   ─────
role = 'Seller'                         role = 'Owner'
role = 'Customer'  ──▶ customers        role = 'Manufacturer' ──▶ suppliers
        (içeriden dışarıya satan)                (dışarıdan içeriye mal satan)
```

FK'nin yönü değil **hedefi** değişti: `customer_id` gitti, `supplier_id` geldi.
Sisteme dışarıdan giren taraf artık müşteri değil, tedarikçi.

```sql
CREATE TABLE users (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    username              varchar(100)  NOT NULL,
    normalized_username   varchar(100)  NOT NULL,   -- ToUpperInvariant()
    password_hash         text          NOT NULL,

    full_name             varchar(200)  NOT NULL,

    role                  varchar(20)   NOT NULL,
    supplier_id           bigint        NULL,       -- Manufacturer ise zorunlu

    last_login_at         timestamptz   NULL,

    is_active             boolean       NOT NULL DEFAULT true,
    created_at            timestamptz   NOT NULL DEFAULT now(),
    updated_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_users_supplier
        FOREIGN KEY (supplier_id) REFERENCES suppliers(id) ON DELETE RESTRICT,
    CONSTRAINT chk_users_role
        CHECK (role IN ('Owner', 'Manufacturer')),
    CONSTRAINT chk_users_role_supplier_consistency
        CHECK (
            (role = 'Owner'        AND supplier_id IS NULL) OR
            (role = 'Manufacturer' AND supplier_id IS NOT NULL)
        ),
    CONSTRAINT chk_users_username_format
        CHECK (username ~ '^[A-Za-z0-9._-]{3,50}$'),
    CONSTRAINT chk_users_normalized_username_format
        CHECK (normalized_username ~ '^[A-Z0-9._-]{3,50}$'),
    CONSTRAINT chk_users_full_name_not_blank
        CHECK (btrim(full_name) <> '')
);

CREATE UNIQUE INDEX ux_users_normalized_username ON users (normalized_username);
CREATE INDEX ix_users_supplier_id ON users (supplier_id);
```

#### 🇹🇷 Türkçe "i" tuzağı — `username` neden ASCII ile sınırlı

Kullanıcı adı büyük/küçük harf duyarsız olmalı ("Ahmet" = "ahmet"), bu yüzden
normalize edilmiş bir kopya ayrı kolonda saklanır. Ama Türkçe'de:

| İşlem | İngilizce | Türkçe |
|---|---|---|
| `"I".ToLower()` | `"i"` | **`"ı"`** ← farklı harf |
| `"i".ToUpper()` | `"I"` | **`"İ"`** ← farklı harf |

Sunucunun kültür ayarı Türkçe ise `"ISIK"` → `"ısık"`, İngilizce ise `"isik"` olur.
Sunucu Windows'tan Linux'a taşınır veya bölge ayarı değişirse **mevcut kullanıcılar
giriş yapamaz hale gelir** — bulması çok zor bir hata.

İki katmanlı çözüm:
1. **C# tarafı:** `ToUpperInvariant()` — kültürden bağımsız, deterministik.
   (`ToUpper()` **değil**.)
2. **DB tarafı:** `CHECK (username ~ '^[A-Za-z0-9._-]{3,50}$')` — sorunun kaynağı
   kökten kurutulur. Pratikte kısıtlayıcı değil: `ahmet`, `anadolu`, `ege_deri`
   hepsi geçerli. Türkçe isimler zaten `full_name` alanında görünür.

#### `full_name` neden eklendi (v1'de yoktu)

`order_history`, `audit_logs`, `payments` tablolarının hepsi `..._by_user_id` tutuyor.
Ekranda gösterirken:

```
❌ "Sipariş #1042 — kullanıcı 3 tarafından sevk edildi"
✅ "Sipariş #1042 — Ahmet Gündoğdu tarafından sevk edildi"
```

`username` teknik bir kimliktir, insan okumaz. Görüntülenecek isim ayrı olmalı.

#### `chk_users_role_supplier_consistency` — bu tablonun kalbi

Tekrar Eden Desen #1'in en kritik uygulaması. İki yönlü koruma:

- `Owner`'a yanlışlıkla `supplier_id` verilirse → reddedilir.
  *(Yoksa bizim hesabımız bir üreticiye bağlanır, yetki karmaşası doğar.)*
- `Manufacturer` `supplier_id` olmadan oluşturulursa → reddedilir.
  *(Yoksa "hangi üreticinin siparişlerini göreceği" belirsiz kalır; RBAC filtresi
  çöker ve potansiyel olarak **tüm** siparişler görünür.)*

İkincisi doğrudan bir **güvenlik açığı senaryosudur**. Uygulama kodunda unutulsa bile
veritabanı geçirmez — savunma derinliği (defense in depth) tam olarak budur.

#### Diğer gerekçeler

- **`password_hash` → `text`** — Hash uzunluğu algoritmaya göre değişir (bcrypt ~60,
  Argon2 daha uzun). PostgreSQL'de `text` ile `varchar(n)` arasında performans farkı
  yoktur; gereksiz sınır konmaz, algoritma değişse şema değişmez.
- **`ux_users_normalized_username`** — `Ahmet` kayıtlıysa `ahmet`/`AHMET` ikinci kez
  kaydedilemez.
- **`ix_users_supplier_id`** — Tekrar Eden Desen #4. Bu index olmadan "bu üreticinin
  kullanıcıları kimler?" sorgusu tüm tabloyu tarar.
- **`last_login_at`** — *"Ege Deri hesabı açıldı ama 3 aydır hiç girmemiş"* → telefon
  aç. Ayrıca terk edilmiş hesap tespiti.

#### Bilinçli olarak ERTELENEN alanlar (Faz 5)

| Alan | Ne işe yarar | Neden şimdi değil |
|---|---|---|
| `failed_login_attempts`, `locked_until` | Kaba kuvvet saldırısına karşı hesap kilitleme | VPS'e geçince (API internete açılınca) gerekli olacak; Aşama 1'de tek PC'de anlamsız |
| `must_change_password` | Üreticiye verilen ilk şifreyi değiştirmeye zorlama | Şifre akışıyla birlikte tasarlanmalı |
| `password_changed_at` | Şifre yaşı takibi | Aynı sebep |

EF Core migration ile eklemek birkaç dakikalık iştir; kullanılmayacak kolonları
şimdiden taşımanın anlamı yok.

#### Kurulum notu

Sistemde **en az bir `Owner` bulunmalıdır**, yoksa kimse giriş yapamaz. DB kısıtıyla
zorlanamaz (çok satırlı kural). Çözüm: kurulum sihirbazı ilk `Owner` hesabını
oluşturur (Faz 5).

#### Stok kodu: üç katmanlı doğrulama

`GND` öneki **veritabanına gömülmez** — yazılım `ABC` önekli bir toptancıya satılınca
şema değişmek zorunda kalmamalı. Şema tüm kurulumlarda aynıdır; bu, "tek kod tabanı"
ilkesinin veritabanı karşılığıdır.

| Nerede | Ne doğrular |
|---|---|
| DB `CHECK` | Genel şekil: 2-5 büyük harf + 4-8 rakam. `abc123`, `GND-142` asla giremez |
| `store_profile` | Bu kurulumun kuralı: önek `GND`, hane `6` |
| Application | Sıradaki kodu üretir, öneki ve hane sayısını doğrular |

`varchar(15)`: senin formatın `GND000142` = 9 karakter, ama white-label tavanı
`ABCDE12345678` = 13 karakter. 15 rahat bir sınır.

`ux_products_stock_code` sadece veri bütünlüğü değil **hız** meselesi: kullanıcı `142`
yazar, uygulama `GND000142`'ye çevirir, bu index sayesinde milisaniyede bulunur.

#### `supplier_id` — kısıt değil, ipucu

> **Bir alışın gerçek üreticisi `purchase_orders.supplier_id`'dir. Buradaki alan
> yalnızca varsayılandır.**

Değerlendirilen alternatifler:

| Seçenek | Neden seçilmedi |
|---|---|
| `NOT NULL` (modele kilitli) | Üretici değişince veya aynı model ikinci yere yaptırılınca çakılır |
| Kolon yok | Her siparişte üreticiyi elle seçmek — hız hedefine aykırı |
| Ayrı `supplier_products` tablosu | Over-engineering; birkaç üretici var, tam tedarik yönetimi kurmuyoruz |

Seçilen (nullable varsayılan) ile: normal durumda sıfır tık, istisnada kapı açık.
Yan fayda: *"Anadolu Ayakkabı'dan hangi modelleri alıyorum?"* tek sorgu.

> 🎨 **UI gereksinimi (Faz 12):** Satın alma siparişi ekranında üretici alanı bu
> varsayılanla dolu gelmeli ama **kilitli olmamalı** — kullanıcı değiştirebilmeli.

#### `supplier_product_code`

Biz `GND000142` diyoruz, üretici `MDL-7734-B` diyor. Sipariş fişinde ikisi de bulunmalı
ki üretici ne üreteceğini anlasın. "Varsayılan + snapshot" deseni: varsayılan burada
durur, satın alma siparişi oluşturulurken kaleme kopyalanır.

#### `gender` / `season`

Ayakkabıcılıkta iki doğal kırılım. `category` serbest metniyle de yazılabilirdi
(*"Kadın Kışlık Bot"*) ama ayrı kolon olunca filtreleme ve raporlama güvenilir olur.

Değerler şemanın geri kalanıyla tutarlı olsun diye **İngilizce** (`customer_type`,
`role` ile aynı desen); ekranda Türkçe gösterilir.

**Nullable bırakıldı:** UI'da pratikte zorunlu gibi davranacak (son seçilen değer
hatırlanır, tek tık), ama DB katmanı esnek kalıyor — toplu içe aktarma veya eski bir
kayıt bu yüzden bloke olmamalı.

#### Diğer gerekçeler

- **`brand` / `category` düz metin, lookup tablo değil** — v1 kararı korundu. Risk
  biliniyor: `"Nike"` / `"nike"` / `"NIKE"` üç ayrı değer olur ve filtreleme bozulur.
  Ama lookup tablo + FK + yönetim ekranı = üç birim iş, henüz gerçek ihtiyaç yok.
  Çözüm UI'da: marka alanı **autocomplete**, mevcut değerleri önerir. Tutarsızlık
  büyürse Faz 7'de normalize edilir.
- **`supplier_id` nullable** — Yeni model tanımlanırken üreticisi henüz bilinmiyor
  olabilir; zorunlu yapmak veri girişini gereksiz bloke eder.
- **`ON DELETE RESTRICT`** — Üretici silinmeye kalkılırsa bağlı ürünler yüzünden
  engellenir.

### Tablo 6/22 — `product_variants`

Bir modelin beden+renk kırılımı. **Stoğun ve fiyatın gerçek taşıyıcısı** — sipariş
kalemleri, stok hareketleri, envanter hep buraya bağlanır.

```sql
CREATE TABLE product_variants (
    id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id       bigint        NOT NULL,

    size             varchar(20)   NOT NULL,
    color            varchar(50)   NOT NULL,   -- normalize edilmiş (ToUpperInvariant)

    barcode          varchar(50)   NULL,

    purchase_price   numeric(18,2) NOT NULL,
    sale_price       numeric(18,2) NOT NULL,

    is_active        boolean       NOT NULL DEFAULT true,
    created_at       timestamptz   NOT NULL DEFAULT now(),
    updated_at       timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_product_variants_product
        FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT,
    CONSTRAINT chk_product_variants_size_trimmed
        CHECK (size = btrim(size) AND size <> ''),
    CONSTRAINT chk_product_variants_color_trimmed
        CHECK (color = btrim(color) AND color <> ''),
    CONSTRAINT chk_product_variants_purchase_price_nonneg
        CHECK (purchase_price >= 0),
    CONSTRAINT chk_product_variants_sale_price_nonneg
        CHECK (sale_price >= 0)
);

CREATE UNIQUE INDEX ux_product_variants_product_size_color
    ON product_variants (product_id, size, color);
CREATE UNIQUE INDEX ux_product_variants_barcode
    ON product_variants (barcode) WHERE barcode IS NOT NULL;
CREATE INDEX ix_product_variants_product_id
    ON product_variants (product_id);
```

#### Karar 1: `sku` kolonu KALDIRILDI

v1'de `sku` zorunlu ve benzersizdi. Analiz sonucu kaldırıldı çünkü:

```
SKU = f(stock_code, size, color)   →  türetilmiş değer
```

Kilitli ilkemiz: *"Türetilebilen değerler bağımsız alan olarak saklanmaz."*
`quantity_available` saklanmadığı gibi `sku` da saklanmaz. Saklansaydı: birisi bir
varyantın rengini düzeltir, `sku` eski haliyle kalır, ikisi çelişir — klasik
senkronizasyon hatası.

**Kimliği ne sağlıyor:** `UNIQUE (product_id, size, color)`. Görüntülenecek kod
(`GND000142-41-SİYAH`) Application katmanında anlık üretilir; ekranda ve etikette
gösterilir, saklanmaz.

**Kaybedilen bir şey yok:** `barcode` duruyor (opsiyonel, benzersiz) — fiziksel
etiket/okuyucu işi onunla yürür. Dış sistem entegrasyonu V1 kapsamında değil.

#### Karar 2: 🚨 `color` tutarsızlığı — veri bütünlüğü riski

`brand` için "düz metin yeter, autocomplete'le hallederiz" denmişti. **`color` için
aynı şey geçerli değil**, çünkü `color` UNIQUE kısıtının parçası:

| Kayıt | Sonuç |
|---|---|
| `(GND142, 41, 'Siyah')` | ✅ Kabul |
| `(GND142, 41, 'siyah')` | ✅ **Kabul!** — farklı metin sayılır |

İki ayrı varyant oluşur ve **stok ikiye bölünür**: 20 çift "Siyah"ta, 15 çift
"siyah"ta. `brand` tutarsızlığı kozmetikti (filtrede iki satır), bu **veri bütünlüğü
hatası**.

Değerlendirilen çözümler:

| | Yöntem | Karar |
|---|---|---|
| A | Uygulama normalize eder (`ToUpperInvariant`) + DB `btrim` kontrolü + UI dropdown | ✅ **Seçildi** |
| B | Ayrı `colors` lookup tablosu + FK | Savunulabilir ama 23. tabloyu getirir |
| C | DB'de `upper(color)` ile fonksiyonel unique index | ❌ **Elendi** — `upper()` veritabanının dil ayarına bağlı; Türkçe 'i' tuzağı `users` tablosundakiyle aynı, DB seviyesinde daha tehlikeli |

Seçilen (A): renk büyük harfe normalize edilmiş saklanır (`SİYAH`), UI mevcut renkleri
dropdown olarak sunar ("yeni renk ekle" seçeneğiyle). Yeni tablo maliyeti yok, hız
kazancı var — yazmak yerine seçmek.

#### Gerekçeler

- **`size varchar(20)`, sayısal değil** — Ayakkabı bedenleri `42`, `42.5`, `42 2/3`
  gibi kesirli/özel notasyon alabilir; sayısal tip bunları taşıyamaz.
- **`CHECK (size = btrim(size) AND size <> '')`** — İki iş birden: boş string engeli
  (Desen #2) **ve** baştaki/sondaki boşluk yasağı. İkincisi yeni ve önemli: `'41'` ile
  `'41 '` farklı metinlerdir, UNIQUE index bunları ayrı sayar → görünmez mükerrer
  varyant. Aynısı `color` için de uygulandı.
- **`sale_price >= purchase_price` kısıtı bilinçli olarak YOK** — Zararına satış meşru
  bir iş kararıdır (elde kalmış modeli maliyetin altına satmak). Veri bütünlüğü kuralı
  değil; Application katmanı uyarabilir, DB engellememelidir.
- **Fiyatlar varyant seviyesinde (v1 kararı korundu)** — Pratik sorun: *"GND142'nin
  fiyatını 850'ye çıkar"* dendiğinde 24 varyant güncellenmeli. **Çözüm şemada değil
  UI'da:** toplu fiyat güncelleme, varyantları tıklayarak seçme imkânıyla (Faz 7).
  *(Alternatif — fiyatı `products`'ta tutup varyantta opsiyonel override — her fiyat
  okumasına `COALESCE` mantığı eklerdi; bu ölçekte toplu düzenleme daha basit.)*
- **`ON DELETE RESTRICT`** — Ürün silinmeye kalkılırsa varyantları yüzünden engellenir.

"Koz ekran" hangi bedenleri göstereceğini **bu tablodan** öğrenir: o ürün için hangi
varyantlar tanımlıysa ızgarada o kutucuklar çıkar. Ayrı bir "beden seti" tablosuna
veya yapılandırmasına gerek yok. Ürün oluştururken "39-45 arası oluştur" gibi toplu
varyant üretimi UI kolaylığı olarak eklenir.

### Tablo 7/22 — `inventory`

Varyant başına **anlık** stok bakiyesi. Hareket geçmişi ayrı tabloda
(`inventory_movements`) — "bakiye + defter" deseni.

```sql
CREATE TABLE inventory (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_variant_id    bigint        NOT NULL,

    quantity_on_hand      integer       NOT NULL DEFAULT 0,
    quantity_reserved     integer       NOT NULL DEFAULT 0,
    quantity_available    integer       GENERATED ALWAYS AS
                                        (quantity_on_hand - quantity_reserved) STORED,

    low_stock_threshold   integer       NOT NULL DEFAULT 0,

    created_at            timestamptz   NOT NULL DEFAULT now(),
    updated_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_inventory_product_variant
        FOREIGN KEY (product_variant_id) REFERENCES product_variants(id) ON DELETE RESTRICT,
    CONSTRAINT chk_inventory_on_hand_nonneg
        CHECK (quantity_on_hand >= 0),
    CONSTRAINT chk_inventory_reserved_nonneg
        CHECK (quantity_reserved >= 0),
    CONSTRAINT chk_inventory_reserved_le_on_hand
        CHECK (quantity_reserved <= quantity_on_hand),
    CONSTRAINT chk_inventory_low_stock_nonneg
        CHECK (low_stock_threshold >= 0)
);

CREATE UNIQUE INDEX ux_inventory_product_variant_id
    ON inventory (product_variant_id);
```

#### Neden `product_variants`'a kolon değil de ayrı tablo

İlişki 1:1 olduğu için haklı bir soru. Üç sebep:

1. **Değişim sıklığı farklı.** Ürün bilgisi nadiren değişir, stok gün içinde onlarca
   kez. Ayrı tablo = ayrı disk sayfası; küçük ve sıcak bir tablo daha verimli
   güncellenir.
2. **🔑 Kilitleme — asıl sebep.** Faz 4'te eşzamanlılık için stok satırı
   kilitlenecek:
   ```sql
   SELECT * FROM inventory WHERE product_variant_id = 42 FOR UPDATE;
   ```
   Bu kilit sürerken aynı varyantın stoğuna kimse dokunamaz (son çift için iki sipariş
   yarışırsa biri bekler), **ama ürün bilgisi okumaları serbest kalır** (katalog,
   arama, fiyat). Stok `product_variants` içinde bir kolon olsaydı, stok kilidi ürün
   okumalarını da bloke ederdi.
3. **Kavramsal ayrım.** "Ürün nedir" ile "elimde kaç tane var" farklı sorulardır.

#### `quantity_available` — üretilmiş kolon (generated column)

Elle yazılamaz; her `INSERT`/`UPDATE`'te otomatik hesaplanıp diske yazılır. Tutarlılık
uygulama koduna bırakılmaz — **hangi kod yazarsa yazsın** doğru değer oluşur.

`STORED` (diske yazılır) vs `VIRTUAL` (okuma anında hesaplanır): PostgreSQL şu an
yalnızca `STORED` destekliyor; ayrıca `STORED` olduğu için index'lenebilir.

**"Türetilmiş değer saklama" ilkesine aykırı değil**, çünkü değeri *biz* saklamıyoruz;
veritabanı garanti ediyor, çelişme ihtimali sıfır. Yasaklanan şey elle güncellenen ve
bayatlayabilen kopyalardı.

#### Kritik kısıt `reserved <= on_hand` ve doğurduğu senaryo

*"Elinde olmayanı söz veremezsin"* kuralının DB karşılığı. Şu duruma yol açar ve
**bilerek kabul edilir**:

```
Durum:  Elde 10 çift, Rezerve 10 çift (hepsi siparişlere söz verilmiş)
Olay:   2 çift hasarlı, stoktan düşülmek isteniyor
Sonuç:  on_hand 8 olurdu ama reserved 10 → KISIT İHLALİ, işlem reddedilir
```

**Doğru davranış budur.** Sistem sessizce "8 var ama 10 söz verdim" durumuna düşemez.
Uygulama kullanıcıya net söyler:

> *"Bu üründen 10 çift siparişlere ayrılmış durumda. Stoktan düşmek için önce ilgili
> siparişlerden birini iptal etmelisiniz."*

Karar kullanıcıya bırakılır — hangi müşterinin siparişinin bozulacağına yazılım karar
veremez. (Faz 8, UI.)

#### `low_stock_threshold` ve DB'nin bir sınırı

`store_profile.default_low_stock_threshold` buraya doğrudan bağlanamaz: **PostgreSQL'de
`DEFAULT` başka bir tablodan değer okuyamaz.** Kolon `DEFAULT 0` ile tanımlanır,
Application katmanı yeni varyant oluştururken `store_profile`'dan okuyup yazar.
Trigger ile de yapılabilirdi ama bu ölçekte gereksiz karmaşıklık — iş kuralı zaten
uygulama katmanının işi.

**Eşik neyle karşılaştırılır:** `quantity_available` ile, `quantity_on_hand` ile değil.
Elde 10 çift olup 10'u rezerveyse satılabilir stok 0'dır, uyarı gelmelidir.

```sql
SELECT * FROM inventory WHERE quantity_available <= low_stock_threshold;
```

#### Diğer gerekçeler

- **`integer`, `bigint` değil** — 2 milyar adet fazlasıyla yeterli.
- **1:1 kurulumu** — ayrı `id` PK + `product_variant_id` üzerinde UNIQUE index.
  Alternatif "paylaşılan PK" deseni (`id = product_variant_id`) mümkündü ama 22 tabloda
  tutarlı PK stratejisi sürdürmek daha değerli.
- **Her varyantın stok satırı olmalı** — DB kısıtıyla zorlanamaz (bir tablonun başka
  tabloda satır *bulunmasını* zorlaması normal FK ile yapılamaz). Uygulama sorumluluğu:
  varyant oluşturulurken aynı transaction içinde stok satırı da oluşturulur (Faz 8,
  tek bir "CreateVariant" use-case'i).

#### Doğrulama testleri


### Tablo 8/22 — `orders`

Perakendeciye satış siparişi. **Onay adımı yoktur** — siparişi kendi personelimiz
girer. Fiziksel stok ve cari borç **sevkiyatta** oluşur.

```sql
CREATE SEQUENCE order_number_seq;

CREATE TABLE orders (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    order_number          varchar(30)   NOT NULL,   -- SIP-2026-000142
    customer_id           bigint        NOT NULL,
    created_by_user_id    bigint        NOT NULL,

    order_date            date          NOT NULL DEFAULT CURRENT_DATE,
    expected_ship_date    date          NULL,

    status                varchar(20)   NOT NULL DEFAULT 'Received',

    total_amount          numeric(18,2) NOT NULL DEFAULT 0,

    delivery_address      text          NULL,       -- snapshot
    notes                 text          NULL,

    shipped_at            timestamptz   NULL,
    shipped_by_user_id    bigint        NULL,
    delivered_at          timestamptz   NULL,
    cancelled_at          timestamptz   NULL,
    cancelled_by_user_id  bigint        NULL,
    cancellation_reason   text          NULL,

    created_at            timestamptz   NOT NULL DEFAULT now(),
    updated_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
    CONSTRAINT fk_orders_created_by
        FOREIGN KEY (created_by_user_id) REFERENCES users(id) ON DELETE RESTRICT,
    CONSTRAINT fk_orders_shipped_by
        FOREIGN KEY (shipped_by_user_id) REFERENCES users(id) ON DELETE RESTRICT,
    CONSTRAINT fk_orders_cancelled_by
        FOREIGN KEY (cancelled_by_user_id) REFERENCES users(id) ON DELETE RESTRICT,

    CONSTRAINT chk_orders_status
        CHECK (status IN ('Received','Preparing','Shipped','Delivered','Cancelled')),
    CONSTRAINT chk_orders_total_nonneg
        CHECK (total_amount >= 0),
    CONSTRAINT chk_orders_shipped_fields
        CHECK (
            status NOT IN ('Shipped','Delivered')
            OR (shipped_at IS NOT NULL AND shipped_by_user_id IS NOT NULL)
        ),
    CONSTRAINT chk_orders_delivered_fields
        CHECK (status <> 'Delivered' OR delivered_at IS NOT NULL),
    CONSTRAINT chk_orders_cancelled_fields
        CHECK (
            status <> 'Cancelled'
            OR (cancelled_at IS NOT NULL
                AND cancelled_by_user_id IS NOT NULL
                AND cancellation_reason IS NOT NULL
                AND btrim(cancellation_reason) <> '')
        )
);

CREATE UNIQUE INDEX ux_orders_order_number ON orders (order_number);
CREATE INDEX ix_orders_customer_id        ON orders (customer_id);
CREATE INDEX ix_orders_status             ON orders (status);
CREATE INDEX ix_orders_order_date         ON orders (order_date);
CREATE INDEX ix_orders_created_by_user_id ON orders (created_by_user_id);
```

#### Karar 1: `order_number` üretimi

Kullanıcının gördüğü numara. `id` ile aynı olmamalı — `id` bir uygulama detayı,
`order_number` müşteriyle telefonda konuşurken söylenen şey.

```
SIP  -  2026  -  000142
 │       │         └─ global sıra (yıl başında sıfırlanmaz)
 │       └─ sipariş yılı
 └─ önek (appsettings.json)
```

**Yıl neden sıfırlanmıyor:** Sıfırlansa "yıl + sıra" çiftini birlikte kilitlemek
gerekirdi; eşzamanlı iki siparişte yarış durumu doğar. Sürekli akan bir PostgreSQL
`SEQUENCE` bunu **kilitsiz ve garantili** halleder.

**Boşluklar normaldir:** Bir işlem geri alınırsa o sıra numarası yanar. Sipariş
numarası kesintisiz olmak zorunda değil, **benzersiz** olmak zorunda.

`SIP` öneki `appsettings.json`'da tutulur. `stock_code_prefix` veritabanındaydı çünkü
orada bir `CHECK` formatını etkiliyordu; burada öyle bir bağ yok.

#### Karar 2: Tek durum kolonu

v1'de `approval_status` + `fulfillment_status` diye iki kolon vardı. Onay adımı
kalktığı için tek akış kaldı; iki kolon tutmak ölü karmaşıklık olurdu.

#### Karar 3: `order_date` ayrı alan (yeni)

`created_at` = kaydın sisteme girildiği an. Ama gerçek hayatta *"dün akşam telefonda
aldığım siparişi bu sabah giriyorum"*. Vade hesabı, raporlar, "bu ayki siparişler"
gerçek sipariş tarihine göre olmalı. İki kavram farklı → iki kolon.

`date` tipinde (saat yok) — siparişin "14:32'de alındığı" bilgisinin iş değeri yok.

#### Karar 4: `delivery_address` snapshot

Müşteri adresini sonradan değiştirirse geçmiş siparişin nereye gönderildiği kaybolur.
`order_items`'taki ürün adı snapshot mantığının aynısı. Sipariş oluşturulurken
müşteriden kopyalanır; kullanıcı değiştirebilir ("bu sefer şubeye gönder").

#### ⚠️ Tekrar eden ders: `NULL` ve `CHECK`

İptal kısıtındaki `IS NOT NULL` kontrolü **şarttır**:

```
btrim(NULL) <> ''   →   NULL <> ''   →   NULL   (TRUE değil, FALSE de değil)
```

PostgreSQL `CHECK` kısıtı, sonucu `NULL` olan ifadeyi **geçerli sayar**. Sadece
`btrim(...) <> ''` yazılsaydı `cancellation_reason = NULL` olan bir iptal sessizce
geçer ve gerekçesiz iptal oluşurdu. Bu üç satırlık desen tüm "duruma bağlı zorunlu
metin" kısıtlarında tekrarlanacak.

#### `total_amount` — saklanıyor, ama disiplinle

v1 kararı korundu. Teorik olarak `SUM(order_items)` ile türetilebilir ve "türetilmiş
değer saklama" ilkesine aykırı görünür.

**Neden yine de saklanıyor:** Sipariş listeleri, dashboard ve cari hesap ekranı bu
değeri sürekli okur; her okumada `order_items`'a JOIN + SUM yapmak en sık kullanılan
ekranları yavaşlatır.

**Disiplin şartı:**
- Kalem eklendiğinde/değiştiğinde/silindiğinde **aynı transaction içinde** yeniden
  hesaplanır.
- Sipariş sevk edildikten sonra kalemler değişmez → değer donar.
- Faz 19'da tutarlılık testi: tüm siparişlerde `total_amount = SUM(order_items)` mi?

Yasağın asıl hedefi **elle düzenlenebilen** kopyalardı; burada değer hiçbir zaman elle
girilmiyor. Bilinçli ve gerekçeli istisna.

#### Diğer gerekçeler

- **`shipped_by_user_id` var, `delivered_by` yok** — Sevkiyat kritik bir finansal olay
  (stok düşer, borç yazılır), kimin yaptığı önemli. Teslim ise çoğunlukla kargonun
  teslim ettiği bilginin işlenmesi; operasyonel, sorumluluk taşımıyor.
- **`ix_orders_status`** — *"Sevk bekleyen siparişler"* dashboard'ın en sık sorgusu.
- **`ix_orders_order_date`** — `created_at` yerine `order_date` üzerinde, çünkü iş
  anlamı taşıyan tarih budur.

Kalem yalnızca `product_variant_id` tutsaydı, 6 ay önceki fatura bugün açıldığında
**1.350 TL** görünürdü. Müşteriye 950'den satılmış, sistem 1.350 diyor: cari hesap
tutmaz, kâr analizi çöker, müşteriyle tartışma çıkar.

`product_variant_id` yine de duruyor — raporlama için ("bu varyanttan bu yıl kaç çift
sattım?").

`sku` kolonu kaldırılmıştı; burada da yok. Yerine bileşenleri snapshot'lanıyor
(`stock_code` + `size` + `color`) — zaten SKU'nun kendisi bunlardı.

#### `line_total` — üretilmiş kolon

`quantity × unit_sale_price` her satırda gerekli. Uygulama hesaplayıp yazsaydı drift
riski doğardı (adet güncellenir, tutar unutulur). `inventory.quantity_available` ile
aynı çözüm: veritabanı garanti eder, elle yazılamaz.
`orders.total_amount` bu kolonların toplamıdır.

#### `UNIQUE (order_id, product_variant_id)`

Aynı siparişte aynı varyantın iki satır olmasını engeller:

```
❌ Satır 1: GND000142/41/SİYAH → 3 çift
   Satır 2: GND000142/41/SİYAH → 5 çift
✅ Satır 1: GND000142/41/SİYAH → 8 çift
```

Beden ızgarasında kullanıcı aynı ürünü iki kez ekleyebilir; toplamlar tutsa da liste
kafa karıştırıcı olur ve rezervasyon mantığı iki satırı ayrı işler. UI ikinci eklemede
adetleri **birleştirir**.

Tek engellenen meşru senaryo: aynı siparişte aynı varyantı iki farklı fiyattan satmak.
V1'de indirim/kampanya motoru olmadığı için böyle bir durum yok.

#### ⚠️ Hard-delete yasağıyla görünürdeki çelişki

`order_items` "asla silinmez" listesindeydi, ama sipariş girerken yanlış eklenen satır
silinebilmeli. Ayrım:

| Sipariş durumu | Kalem silinebilir mi |
|---|---|
| `Received` / `Preparing` | ✅ Sipariş henüz taslak, finansal sonuç doğmamış |
| `Shipped` / `Delivered` | ❌ Stok düşmüş, borç yazılmış, tarih olmuş |
| `Cancelled` | ❌ İptal kaydı olduğu gibi kalır |

Yasak **finansal sonuç doğmuş** kayıtlar içindir. Kural DB trigger'ıyla da
zorlanabilirdi ama Application katmanında tutuluyor — tek giriş noktası API olduğu için
yeterli, trigger bu ölçekte gereksiz karmaşıklık. (Faz 11 sevkiyat use-case'i,
Faz 19 testi.)

#### Gerekçeler

- **`quantity > 0`, `>= 0` değil** — 0 adetlik kalem anlamsızdır. `orders.total_amount
  >= 0` idi (boş sipariş 0 TL olabilir) ama kalem seviyesinde sıfır kabul edilmez.
  Bilinçli ayrım.
- **🔴 `unit_purchase_price` gizlilik notu** — Kâr marjını ele verir. Üretici satış
  siparişlerini zaten hiç göremez (RBAC), ama kural net: bu alan **hiçbir üretici
  DTO'sunda bulunmaz**. Faz 19'da gizlilik testi doğrulayacak.
- **Alış fiyatı neden snapshot'lanıyor** — Geçmişe dönük kâr analizi için: *"Ağustos'ta
  bu modelden ne kâr ettim?"* o günkü alış-satış farkını gerektirir; bugünkü alış
  fiyatıyla hesaplanırsa yanlış sonuç çıkar.
- **`updated_at` yok** — Kalem sevk sonrası değişmiyor; sevk öncesi değişiklikler
  `orders.updated_at` üzerinden izleniyor.

Bunu `audit_logs`'un `jsonb` verisinden üretmek hem sorgu olarak ağır hem kod olarak
çirkin olurdu. **Aynı bilginin iki amaç için iki biçimde tutulması tekrar değil, doğru
tasarımdır.**

#### Alanların kullanımı

| `event_type` | `old_value` | `new_value` | `note` |
|---|---|---|---|
| `Created` | — | — | — |
| `ItemAdded` | — | `GND000142/41/SİYAH ×12` | — |
| `ItemChanged` | `×12` | `×10` | — |
| `ItemRemoved` | `GND000142/43/SİYAH ×4` | — | `Stok yetmedi` |
| `StatusChanged` | `Received` | `Preparing` | — |
| `StatusChanged` | `Preparing` | `Cancelled` | `Müşteri vazgeçti` |
| `ExpectedShipDateChanged` | `2026-09-01` | `2026-09-05` | `Üretim gecikti` |

#### Gerekçeler

- **`old_value`/`new_value` `text`, `jsonb` değil** — Bu tablonun tek işi ekranda
  okunabilir bir satır göstermek. `jsonb` olsaydı her olay tipi için ayrı bir
  "Türkçeye çevir" kodu gerekirdi. Metin olarak saklanınca uygulama bir kez formatlar,
  ekran doğrudan basar. Makine-okunur ihtiyaç `audit_logs`'un işi — orada `jsonb`
  kullanılacak. **İki tablo, iki farklı doğru cevap.**
- **`changed_by_user_id` `NOT NULL`** — V1'de her olayın bir faili var; otomatik iş
  yok. İleride "sistem gece otomatik iptal etti" gelirse nullable yapılır veya bir
  `system` kullanıcısı tanımlanır.
- **Bileşik index `(order_id, changed_at)`** — Bu tablonun %95 kullanımı tek sorgu:
  `WHERE order_id = ? ORDER BY changed_at`. Bileşik index hem filtreyi hem sıralamayı
  karşılar; DB ayrıca sıralama yapmaz. Sadece `(order_id)` olsaydı bulunan satırları
  ayrıca sıralaması gerekirdi.

Üreticiye verdiğimiz sipariş. **Üreticinin gördüğü tek veri** — gizlilik kuralının

#### Karar 1: Durum akışı — iki taraf da dokunuyor

Satış siparişinde tek taraf vardı. Burada iki taraf var; kimin neyi değiştirebileceği
kritik.

```
  BİZ                    ÜRETİCİ                        BİZ
 Draft ──▶ Sent ──▶ InProduction ──▶ Ready ──▶ Shipped ──▶ Completed
   │                                                          
   └──────────────────── Cancelled ◀─────────────────────────┘
```

| Durum | Anlamı | Kim değiştirir |
|---|---|---|
| `Draft` | Hazırlanıyor — **üretici GÖREMEZ** | Biz |
| `Sent` | Üreticiye iletildi | Biz |
| `InProduction` | Üretimde | **Üretici** |
| `Ready` | Sevke hazır | **Üretici** |
| `Shipped` | Üretici yola çıkardı | **Üretici** |
| `Completed` | Bizce kapandı | Biz |
| `Cancelled` | İptal | Biz |

**`Draft` neden kritik:** Sipariş hazırlarken adetler değişir, fikir değişir, satır
silinir. Üretici bunu canlı izlememeli. Bu, üretici sorgularına
`AND status <> 'Draft'` filtresi demek (Faz 12, RBAC).

#### Karar 2: Teslim durumu saklanmıyor, türetiliyor

`PartiallyReceived`/`FullyReceived` durumları **eklenmedi** — bilgi zaten kalemlerde:

```sql
SUM(received_quantity) = 0                 → Beklemede
0 < SUM(received) < SUM(ordered)           → Kısmi Teslim
SUM(received) = SUM(ordered)               → Tamamlandı
```

Saklansaydı drift riski doğardı (mal kabul yapılır, durum güncellenmeyi unutulur).
Tek doğruluk kaynağı ilkesi.

#### Karar 3: `Completed` ≠ "hepsi geldi"

> *"500 çift sipariş verdim, 480 geldi, kalan 20'yi üretici yapamayacak. Kapatıyorum."*

Teslim durumu "Kısmi" kalır ama sipariş **kapanmıştır**. Bu bir iş kararıdır,
hesaplanamaz — birinin "bu iş bitti" demesi gerekir. Bu yüzden `Completed` gerçek bir
durumdur, türetilmiş değer değil.

#### Karar 4: Vade tarihi mal kabulde belirlenir

`payment_due_date` nullable ve **sipariş anında değil mal kabulde** dolar. Vade malın
gelişinden (veya faturadan) başlar: 1 Eylül'de sipariş verilip 15 Ekim'de mal
alınıyorsa 90 günlük vade 15 Ekim'den işler.
`suppliers.default_payment_term_days` kullanılarak otomatik hesaplanır.

#### 🔴 Gizlilik: üreticiye ne gider, ne gitmez

| Kolon | Üretici görür mü |
|---|---|
| `purchase_order_number`, `order_date`, `expected_delivery_date` | ✅ |
| `status`, `supplier_reference` | ✅ |
| `notes` | ✅ — bu alan üreticiye **mesaj** kutusudur |
| `total_amount` | ✅ — kendi sattığı malın tutarı, zaten biliyor |
| `payment_due_date` | ✅ — ne zaman ödeme yapacağımız |
| **`internal_notes`** | ❌ **ASLA** — iç değerlendirme/uyarı |
| Başka üreticinin siparişleri | ❌ **ASLA** — `WHERE supplier_id = <kendi id'si>` |
| `Draft` durumundakiler | ❌ Henüz gönderilmemiş |
| `created_by_user_id`, `completed_by_user_id` | ❌ İç personel bilgisi |

> **`notes` / `internal_notes` ayrımı neden şart:** Tek bir not alanı olsaydı kullanıcı
> ister istemez oraya *"bu üretici geçen sefer geç kaldı, sıkı takip et"* gibi iç
> değerlendirmeler yazardı ve üretici bunları okurdu. UI'da iki ayrı kutu olacak; iç
> not kutusunun üstünde net etiket: *"Bu not üreticiye gösterilmez."*

`orders`, `customers`, `account_transactions` tablolarına **hiç erişimi yok** — tablo
seviyesinde yapısal izolasyon.

#### Diğer gerekçeler

- **`ALS` öneki** — `SIP` (satış) ile karışmasın diye; `appsettings.json`'da tutulur.
- **`supplier_reference`** — Telefonda *"sizin 2026/443 nolu sipariş"* dendiğinde kendi
  numaranı bulabilmek için. İki dünyayı bağlar.
- **`chk_purchase_orders_sent_fields` ters mantıkla** — "Draft veya Cancelled değilse
  `sent_at` dolu olmalı". `Cancelled` istisnadır: sipariş gönderilmeden de iptal
  edilebilir (yanlış hazırlandı).
- **`supplier_shipped_at` var, `production_started_at`/`ready_at` yok** — Sevk anı
  operasyonel olarak önemli ("yolda, ne zaman gelir?"). Diğer geçişler
  `purchase_order_history`'de zaten kayıtlı; ayrı kolon gereksiz şişkinlik.
- **`total_amount` saklanıyor** — `orders` ile aynı gerekçe ve aynı disiplin.
- **`ix_purchase_orders_payment_due`** — *"Bu hafta hangi üreticiye ödeme yapmam
  lazım?"* dashboard sorgusu; "amiral gemisi" hedefinin somut karşılığı.

Kısmi teslimat mantığının yaşadığı yer. `order_items` ile kardeş, üç önemli farkla.

```sql
CREATE INDEX ix_purchase_order_items_product_variant_id

```

#### Fark 1: İki miktar kolonu

Satış tarafında tek miktar yeterliydi (sevk ya yapılır ya yapılmaz). Alışta **kısmi
teslimat normaldir**:

```
1 Eylül :  500 çift sipariş  →  ordered=500, received=0
15 Ekim :  320 çift geldi    →  ordered=500, received=320   (Kısmi)
2 Kasım :  180 çift geldi    →  ordered=500, received=500   (Tamamlandı)
```

`received_quantity` **birikimlidir** — her mal kabulde üzerine eklenir.

#### Fark 2: İki tutar kolonu

| Kolon | Formül | Anlamı |
|---|---|---|
| `line_total` | `ordered × unit_purchase_price` | **Taahhüt ettiğimiz** tutar |
| `received_total` | `received × unit_purchase_price` | **Borçlandığımız** tutar |

`purchase_orders.total_amount` = `SUM(line_total)` → siparişin büyüklüğü.
Üreticiye borcumuz = `SUM(received_total)` → **gelmeyen malın parası ödenmez.**

İkisi de üretilmiş kolon; veritabanı garanti eder, drift olamaz.

#### Fark 3: Fazla teslimat engellenmiyor (bilinçli)

`CHECK (received_quantity <= ordered_quantity)` **yazılmadı**. Gerekçe:

> *"480 çift sipariş ettim, üretici 500 gönderdi."*

Bu gerçek hayatta olur. DB engellerse operatör gerçeği kaydedemez ve muhtemelen 480
girip **20 çifti stok dışı bırakır** — o 20 çift depoda durur ama sistemde yoktur.

Tercih sırası net: **stok doğruluğu > sipariş düzeni.**

Uygulama fazla teslimatta uyarır (*"Siparişte 480 vardı, 500 giriyorsunuz. Emin
misiniz?"*) ve karar operatöre bırakılır. Yazım hatası (48 yerine 480) bu uyarıyla
yakalanır.

#### Gerekçeler

- **`supplier_product_code` burada da snapshot** — `products`'taki varsayılandan
  kopyalanır. Üretici kendi kodlamasını değiştirirse geçmiş sipariş fişi bozulmasın
  diye. Kullanıcı sipariş anında da değiştirebilir.
- **`updated_at` var (`order_items`'ta yoktu)** — `received_quantity` zaman içinde
  defalarca güncellenir. Satış kalemi ise yazıldıktan sonra donuyordu.
- **Neden ayrı `goods_receipts` tablosu yok** — Gerçek ERP'ler her teslimatı ayrı
  tabloda tutar (23-24. tablolar olurdu). Gerek yok: her teslimatın ayrı kaydı **zaten
  `inventory_movements`'ta** olacak (`movement_type='Purchase'`, `purchase_order_id`
  referansıyla). "15 Ekim'de 320, 2 Kasım'da 180 geldi" bilgisi kaybolmuyor; iki tablo
  daha eklemek aynı bilgiyi ikinci kez tutmak olurdu.
- **Beden ızgarası burada da çalışır** — Satın alma siparişi de "40'tan 50, 41'den 80"
  şeklinde girilir. Faz 10'da yazılacak ızgara bileşeni Faz 12'de aynen yeniden
  kullanılır: tek bileşen, iki ekran.
- **`ordered > 0` ama `received >= 0`** — Sipariş satırı en az 1 adet olmalı; teslim
  alınan başlangıçta 0'dır.

### Tablo 14/22 — `inventory_movements`

Stok hareket defteri. `inventory` *"şu an 17 çift var"* der; bu tablo *"**neden** 17?"*
sorusunu cevaplar. `account_transactions`'ın stok tarafındaki ikizi:
**bakiye + defter.**

> **v1'deki sorun çözüldü:** Pivot öncesi handoff'ta bu tablo için *"`orders`'a FK
> veriyor ama `orders` henüz tasarlanmadı, bu sorunu çözmek gerekiyor"* notu vardı.
> Yeni sıralamada tablo 14. sıraya taşındı; `orders` (8) ve `purchase_orders` (11)
> çoktan hazır. Sorun tartışılarak değil, **doğru sıralamayla yapısal olarak** ortadan
> kalktı.

```sql
CREATE TABLE inventory_movements (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_variant_id    bigint        NOT NULL,

    movement_type         varchar(30)   NOT NULL,
    on_hand_delta         integer       NOT NULL DEFAULT 0,
    reserved_delta        integer       NOT NULL DEFAULT 0,

    order_id              bigint        NULL,
    purchase_order_id     bigint        NULL,

    reason                text          NULL,

    created_by_user_id    bigint        NOT NULL,
    created_at            timestamptz   NOT NULL DEFAULT now(),

    CONSTRAINT fk_inventory_movements_variant
        FOREIGN KEY (product_variant_id) REFERENCES product_variants(id) ON DELETE RESTRICT,
    CONSTRAINT fk_inventory_movements_order
        FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE RESTRICT,
    CONSTRAINT fk_inventory_movements_purchase_order
        FOREIGN KEY (purchase_order_id) REFERENCES purchase_orders(id) ON DELETE RESTRICT,
    CONSTRAINT fk_inventory_movements_created_by
        FOREIGN KEY (created_by_user_id) REFERENCES users(id) ON DELETE RESTRICT,

    CONSTRAINT chk_inventory_movements_type_signature
        CHECK (
            (movement_type = 'InitialStock'        AND on_hand_delta >  0 AND reserved_delta =  0) OR
            (movement_type = 'Purchase'            AND on_hand_delta >  0 AND reserved_delta =  0) OR
            (movement_type = 'Return'              AND on_hand_delta >  0 AND reserved_delta =  0) OR
            (movement_type = 'ManualIncrease'      AND on_hand_delta >  0 AND reserved_delta =  0) OR
            (movement_type = 'OrderReservation'    AND on_hand_delta =  0 AND reserved_delta >  0) OR
            (movement_type = 'ReservationReleased' AND on_hand_delta =  0 AND reserved_delta <  0) OR
            (movement_type = 'Sale'                AND on_hand_delta <  0 AND reserved_delta <= 0) OR
            (movement_type = 'ManualDecrease'      AND on_hand_delta <  0 AND reserved_delta =  0) OR
            (movement_type = 'Damaged'             AND on_hand_delta <  0 AND reserved_delta =  0)
        ),
    CONSTRAINT chk_inventory_movements_manual_reason
        CHECK (
            movement_type NOT IN ('ManualIncrease','ManualDecrease','Damaged')
            OR (reason IS NOT NULL AND btrim(reason) <> '')
        ),
    CONSTRAINT chk_inventory_movements_order_link
        CHECK (
            movement_type NOT IN ('Sale','OrderReservation','ReservationReleased')
            OR order_id IS NOT NULL
        )
);

CREATE INDEX ix_inventory_movements_variant_created
    ON inventory_movements (product_variant_id, created_at);
CREATE INDEX ix_inventory_movements_order_id
    ON inventory_movements (order_id);
CREATE INDEX ix_inventory_movements_purchase_order_id
    ON inventory_movements (purchase_order_id);
CREATE INDEX ix_inventory_movements_type_created
    ON inventory_movements (movement_type, created_at);
CREATE INDEX ix_inventory_movements_created_by
    ON inventory_movements (created_by_user_id);
```

#### Ne işe yaradığı

```
inventory:  GND000142/41/SİYAH  →  on_hand = 17

inventory_movements:
  01 Eyl  InitialStock         +20    Açılış sayımı
  05 Eyl  OrderReservation       0  (+3 rezerve)   SIP-2026-000001
  08 Eyl  Sale                  -3  (-3 rezerve)   SIP-2026-000001
  12 Eyl  Damaged               -2    Kutu ezilmiş, satılamaz
  15 Eki  Purchase              +2                 ALS-2026-000003
                              ─────
                                17  ✓
```

#### Dokuz hareket tipi ve işaret imzaları

| Hareket tipi | `on_hand_delta` | `reserved_delta` | Ne zaman |
|---|---|---|---|
| `InitialStock` | **+** | 0 | Sisteme ilk giriş / açılış sayımı |
| `Purchase` | **+** | 0 | Üreticiden mal kabul |
| `Return` | **+** | 0 | Müşteriden iade |
| `ManualIncrease` | **+** | 0 | Sayım fazlası |
| `OrderReservation` | 0 | **+** | Sipariş alındı, mal ayrıldı |
| `ReservationReleased` | 0 | **−** | Sipariş iptal, mal serbest |
| `Sale` | **−** | **−** | Sevkiyat: stok düşer **ve** rezerve serbest kalır |
| `ManualDecrease` | **−** | 0 | Sayım eksiği, kayıp |
| `Damaged` | **−** | 0 | Hasarlı, satılamaz |

`Sale`'in iki kolonu birden etkilemesi yeni akışın kalbidir: sipariş alındığında
rezerve edilen mal, sevk anında hem fiziksel stoktan düşer hem rezervasyonu bırakır.

#### İmzaların DB'de zorlanması

Bu tablo stoğun hesap defteridir; içine anlamsız kayıt girerse stok açıklanamaz hale
gelir. Tek bir `CHECK` her tipin işaret yönünü zorlar.

**Yan fayda:** Bu `CHECK` aynı zamanda geçerli tip listesini de zorlar — listede
olmayan bir tip hiçbir dala uymaz ve reddedilir. Ayrıca `movement_type IN (...)`
kısıtı yazmaya gerek kalmaz. **Tek kısıt, iki iş.**

#### Manuel hareketlerde gerekçe zorunlu

Otomatik hareketlerin gerekçesi zaten bellidir (bağlı olduğu sipariş). Ama biri elle
stoğa dokunuyorsa **neden dokunduğunu yazmak zorundadır.** Denetlenebilirliğin en
somut noktası: 3 ay sonra "bu 5 çift nereye gitti?" sorusunun cevabı orada durur.

#### Gerekçeler

- **`Sale` için `reserved_delta <= 0`, `< 0` değil** — Sıkı yazmak daha temiz
  görünürdü, ama rezervasyonu bir şekilde düşmüş bir siparişi sevk etmek gerekirse
  sıkı kısıt **tüm sevkiyat transaction'ını patlatır** ve mal gönderilemez. Tercih:
  *defterin gerçeği kaydetmeyi reddetmesindense biraz gevşek olması yeğdir.* (Fazla
  teslimatta da aynı prensip uygulandı.)
- **`purchase_order_id` `Purchase` tipinde bile zorunlu değil** — Sipariş açmadan mal
  alınabilir (üreticiye uğradın, elde kalanı aldın). Meşru senaryo. Satış tarafında
  böyle bir boşluk yok, o yüzden `order_id` zorunlu.
- **`created_by_user_id` `NOT NULL`** — v1'de nullable'dı, değiştirildi: V1'de
  otomatik stok hareketi yok, her hareketin bir faili var. Stok defterinde "kim yaptı
  bilinmiyor" satırı olmamalı.
- **`ix_inventory_movements_type_created`** — *"Bu ay ne kadar hasar yazdım?"*,
  *"Bu hafta kaç mal kabul yaptım?"* rapor sorguları.
- **Append-only** — `updated_at` yok. Yanlış hareket **düzeltme hareketiyle** telafi
  edilir (ters yönlü `ManualIncrease`/`ManualDecrease` + gerekçe), satır güncellenmez.
  Finansal ters kayıt politikasının stok tarafındaki karşılığı.

#### 🏅 Faz 19 için altın test

`inventory` ile bu defterin **her zaman** uyuşması gerekir:

```sql
SELECT i.product_variant_id,
       i.quantity_on_hand,
       COALESCE(SUM(m.on_hand_delta), 0) AS hareket_toplami
FROM inventory i
LEFT JOIN inventory_movements m ON m.product_variant_id = i.product_variant_id
GROUP BY i.product_variant_id, i.quantity_on_hand
HAVING i.quantity_on_hand <> COALESCE(SUM(m.on_hand_delta), 0);
-- Beklenen: 0 satır. Satır dönerse transaction bütünlüğü bir yerde bozulmuş demektir.
```

Aynısı `quantity_reserved` ↔ `reserved_delta` için. Bu iki sorgu, tüm stok mantığının
tek cümlelik sağlamasıdır.
